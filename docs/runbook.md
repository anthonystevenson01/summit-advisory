## Contact Us Form — added March 2026

**Trigger:** User submits the form at `/contact`. The browser POSTs JSON to `/api/contact`.

**Service/Function:** `app/api/contact/route.ts` → `POST` handler. The client-side entry point is `app/contact/ContactForm.tsx` → `handleSubmit`.

**Failure mode:**

- _Client validation fails_ — form displays inline field errors; no network request is made.
- _Network error_ — catch block in `handleSubmit` shows a top-banner error; form data is preserved so the user can retry.
- _Server returns `{ success: false }`_ — banner displays the server's `message` string (or a generic fallback). The form remains editable.
- _Server returns a non-2xx status_ — same banner path as above via the `!response.ok` check.

**Template/Config:** No environment variables or config keys required for the current implementation (submission is logged to stdout only). To wire up an email provider, add the relevant credentials as environment variables and extend the `POST` handler after the `console.log` call.

**To disable:** Return a `503` response at the top of the `POST` handler in `app/api/contact/route.ts`, or add a Next.js middleware redirect for the `/api/contact` path. No deploy is required if the middleware approach is used with an environment-variable feature flag.

**Known limitations / future work:**

- `isValidEmail` is duplicated between `ContactForm.tsx` and `route.ts` — extract to `lib/validation.ts`.
- No rate limiting on `POST /api/contact` — add middleware or WAF rule before production.
- No `aria-live` loading announcement — minor accessibility improvement.

## Summit GTM Toolkit — added April 2026

**Overview:** Five AI-powered diagnostic tools and The Scale-Up Letter newsletter, deployed as new routes on the existing summitstrategyadvisory.com Next.js site. All AI calls are server-side for security and consistency with the existing codebase pattern.

### Routes

**Public-facing:**
- `GET /tools` — GTM Toolkit hub listing five diagnostic tools
- `GET /newsletter` — The Scale-Up Letter publication hub and reading view
- `POST /api/newsletter/signup` — Newsletter signup proxy

**Tool routes (server-side AI):**
- `POST /api/gtm/positioning` — Positioning Statement Grader (letter grade + 6 dimensions)
- `POST /api/gtm/problem` — Market Problem Validator (go/no-go verdict)
- `POST /api/gtm/persona` — Persona Quality Check (grade + 6 dimensions)
- `POST /api/gtm/moat` — Competitive Moat Rater (hexagonal score + moat rating)
- `POST /api/gtm/account` — Account Intelligence (web_search_20250305 + cycling loader)

**Support:**
- `GET /api/prompts` — Notion proxy returning system prompts keyed by tool_id; returns `{}` if Notion unreachable

### Environment Variables

| Variable | Required | Purpose |
|---|---|---|
| `ANTHROPIC_API_KEY` | Yes (existing) | Used for all AI tool calls |
| `NOTION_TOKEN` | No | Notion integration token for fetching system prompts at runtime |
| `NOTION_PROMPTS_DB_ID` | No | Notion GTM Tool Prompts database ID |
| `NEWSLETTER_ENDPOINT` | No | Newsletter platform signup endpoint; graceful "coming soon" if absent |
| `UPSTASH_REDIS_REST_URL` | Yes (existing) | Rate limiting |
| `UPSTASH_REDIS_REST_TOKEN` | Yes (existing) | Rate limiting |

### Notion Setup (optional)

1. Create a Notion database named "GTM Tool Prompts" with properties: `Title` (tool_id string), `Version` (number), `Active` (checkbox), `Notes` (rich text). Prompt text lives in the page body.
2. Add five pages: `positioning`, `problem`, `persona`, `moat`, `account` — tick Active on each.
3. Create a Notion integration, copy the token → `NOTION_TOKEN`.
4. Copy the database ID → `NOTION_PROMPTS_DB_ID`.
5. If Notion is unreachable at runtime, hardcoded fallbacks in `app/components/toolkit/data/fallbackPrompts.ts` are used automatically.

### Deployment Requirements

**Tool 05 (Account Intelligence) requires Vercel Pro or higher.** It uses `web_search_20250305` with `maxDuration = 30`. Free tier times out at 10 seconds and will return 504. All other tools work on any plan.

### Editing the copy

- Edit strings in `app/scale-up-advisory/scale-up-content.ts`. The pages only map this data onto existing `globals.css` classes, so copy changes rarely need a JSX change.
- Keep the module free of runtime imports (`import type` only). The tests load it directly with Node's type stripping, which cannot resolve the `@/` alias or pull in React/Next. The same applies to `next.config.ts`: the redirect test imports it the same way, so a runtime import there means adjusting the test.
- FAQs (`OUTSOURCED_FAQS`, `FRACTIONAL_FAQS`) feed both the visible FAQ and the FAQPage JSON-LD, so they always match. The hub has no FAQ and no FAQPage schema.
- When you make a material copy change, bump `DATE_MODIFIED` (JSON-LD, currently `2026-09-28`) and `LAST_REVIEWED_LABEL` (byline). The test pins `DATE_MODIFIED`, so update the assertion too.
- Copy hygiene is enforced by the test: the deck typos ("guide by", "motion's", "rouge", "small team covers", "Management Consulting") must not reappear, em-dashes in the module are capped at a small number, and the options are never called "routes". That last check runs `/\broutes?\b/i` over the stringified module, which includes export names, so an export called `ROUTES` fails it too. Use "option" or "page".
- The three heroes share `HERO.eyebrow` ("For B2B Scale-Ups"). On the option pages the back link directly above the eyebrow already reads "Scale-Up Advisory", so don't put that text in the eyebrow.
- `HUB_TOOLS.heading` and `.body` must keep saying "AI" and "free"; the test checks both words.
- `PACKAGE_COUNT` (19) is the tested source of truth; `WHAT_SUMMIT_IS.body` spells it out ("Nineteen") and names the first and last stage ("from MAP to GROW"), so change the number, the paragraph and `PACKAGE_STAGES` together. The test checks both the word and the stage span.
- The four outsourced FAQ questions and their order are pinned by the test (`outsourced pitch page` suite), along with the four thesis points, `THESIS.closer`, the five Lead Engine facts and `OUTSOURCED_TOOLS_LINE`. Adding, removing or reordering a question means updating the assertion too.

### Tool-to-stage map

`TOOL_STAGE_MAP` ties each public free tool to the package stage it demonstrates (Problem and ICP → MAP, Persona and Positioning → REACH, Moat → WIN). Names are hardcoded rather than imported. Each entry has a `summary` (what the tool does) and a `stageNote` (how it ties to the stage): the hub shows `summary` only, under a constant "Free tool" tag (no page explains the package stages any more, so a stage name would mean nothing to a visitor). The test checks that every mapped slug is public, `href` is `/tools/<slug>`, the name matches the `TOOL_SEO` title, the stage is a real `PACKAGE_STAGES` id, the `stageNote` names its stage, and the set of public tools equals the set of mapped tools. If you publish or hide a tool (e.g. Account Intelligence), add or remove it here and pick a stage.

### Running the tests

```bash
npm test          # node:test, runs every __tests__/*.test.ts
npm run lint      # ESLint; public/** is ignored
npx tsc --noEmit  # type check
npm run build     # strongest check: validates page exports, metadata and the redirects() entry
```

- **Node ≥ 22.18 (or ≥ 23.6) is required** for `npm test`, because it relies on Node's native TypeScript type stripping. It will fail on Node 20.
- **Tests use `node:test`.** Imports in tests must be relative with explicit `.ts` extensions, and imported modules must not have runtime `@/` alias imports (Node can't resolve them; type-only imports are fine because they are stripped). `gtm-toolkit.test.ts` now runs and pins the hub's `TOOLS` cards (02–05) to public tool slugs.
- **Lint conventions:** prefix intentionally unused vars and args with `_`. The `/?page=` links in `SiteNav` stay `<a>` on purpose (the homepage reads `?page=` only on mount, so a full load is required).
- If `tsc` reports errors only in `.next/types/* 2.ts` (or similarly numbered duplicates), those are generated duplicates in the git-ignored build folder, not source. They appear when `tsc` runs while `next build` is rewriting `.next/types/`, or from Finder copies. Delete them and rerun `tsc`. Run the gates one after another, never `tsc` and `next build` at the same time.

## GTM tool pipeline, routing table and calibration gate, added October 2026

**Trigger:** A visitor scores a tool at `/tools/{slug}` (icp, persona, problem, positioning, moat). `ToolPage.tsx` POSTs to `/api/tools/{slug}/score`; after the unlock form it POSTs to `/api/tools/{slug}/unlock` and then `/api/tools/{slug}/details`. The hidden `account` tool keeps its own route at `/api/gtm/account` and answers 404 while `hidden: true` in the registry.

**Service/Function:**
- `app/lib/tools/registry.ts` describes every tool once. Nothing else holds a dimension, weight, input or SEO string.
- `app/lib/tools/pipeline.ts` exports `scoreRun(slug, inputs, ctx)` (validate against the registry, load the Published rubric and system prompt from Notion, one scoring call at temperature 0 with a JSON schema generated from the registry, score out of 100, grade 1 to 5 on the 85/70/50/30 bands, persist, return the free view) and `detailRun(runId, ctx)` (requires an unlock, one details call for per dimension reasoning, recommendations for dimensions at 3 or below and the tool's extras, persist, return the full view; a second call for the same run is served from Redis).
- Routes: `app/api/tools/[tool]/score/route.ts` (5 scores per IP per tool per hour, `maxDuration = 60`), `app/api/tools/[tool]/details/route.ts` (10 per IP per tool per hour, `maxDuration = 60`), `app/api/tools/[tool]/unlock/route.ts` (name, email, company; records the unlock on the run and appends to `gtm-unlocks` so the daily digest is unchanged). Errors map through `app/api/tools/[tool]/errors.ts`. Any `rubric` or `systemPrompt` field in a request body is dropped.
- `app/lib/llm.ts` is the only model client (OpenRouter through the `openai` package) and the only file that names a model id (`DEFAULT_ROUTES`, `CURATED_MODELS`). `app/lib/rubrics.ts` is the only reader of Notion. `app/lib/runs.ts` is the run store. `app/lib/events.ts` is the event stream.
- Admin: `/admin/runs` (every run, filter by tool, expandable inputs and reasoning), `/admin/models` (the routing table), `/admin/rubrics` (live rubric version, hash, fetched time, refresh button). `/admin` counts come from the run store.

**Failure mode:**
- Rubric row missing or not Published in Notion, or `NOTION_TOKEN` / `NOTION_RUBRICS_DB_ID` unset: 503 `rubric not published`. The tool never scores without a rubric.
- `OPENROUTER_API_KEY` unset: 503 `model provider not configured`.
- Model answer fails the schema validator, or is empty: 502 "The model returned an unusable answer. Please try again." The page shows a retry.
- Details requested before the unlock: 403. Unknown or hidden slug: 404. Expired or unknown run id: 404.
- Rate limit reached: 429 with `Retry-After: 3600`.
- Timeout: one attempt is capped at 40 seconds. A connection error or 5xx inside the first 15 seconds is retried once; a timeout is never retried, so the worst case is about 55 seconds inside the route's 60. A timed out call surfaces as 500 "Something went wrong" and is logged to `ai:calls` with `ok: false`.
- Upstash variables unset: rate limiting is skipped. Redis unreachable: the run is scored but not saved (the page still shows the result; unlock then fails with 404 because the run is not stored), and `ai:calls` and `events` writes are dropped silently. Tracking and call logging never throw and are never awaited on the response path, so on Vercel an entry can occasionally be lost when the function returns first.
- Any other error: 500 with a generic message; the detail is in the function log, never in the response.

**Template/Config:**
- Environment: `OPENROUTER_API_KEY` (all model calls), `NOTION_TOKEN` and `NOTION_RUBRICS_DB_ID` (rubrics and prompts; the database is `dad404fc12af4207bd446e9e8be22330`), `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` (or the `KV_REST_API_*` pair). SMTP and admin variables are unchanged.
- Retired and safe to delete from Vercel: `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, `SKILL_DOC_ID`, `RECOMMENDATIONS_DOC_ID`, `NOTION_PROMPTS_DB_ID` and every `NOTION_*_RUBRIC_ID`.
- Redis keys:

| Key | What | TTL |
|---|---|---|
| `run:{id}` | Hash, one per scored run: inputs, scores, score, grade, verdict, confidence, reasoning, recommendations, extras, rubric version and hash, model per call, calibrated flag per call, unlock | 30 days; removed when the run is unlocked, so unlocked runs persist |
| `runs:by-time` | Sorted set index of run ids by created time | none; `listRuns` prunes expired ids as it reads |
| `rubric:{slug}` | Cached `{ systemPrompt, rubric, version, hash, fetchedAt }` from Notion | 10 minutes, plus a 60 second in memory cache per instance |
| `admin:model-config` | Hash, routing key to `{ model, reasoning?, maxTokens?, fallback? }` override | none; cached in memory for 30 seconds |
| `admin:calibration` | Hash, routing key to `{ model, passedAt, rubricHashes }` or `{ model, uncalibratedSince }` | none |
| `admin:model-catalog` | The curated model list with OpenRouter prices | 10 minutes |
| `ai:calls` | List, one entry per model call: key, model, runId, ms, tokens, cost, ok, error, calibrated | none; capped at the last 2000 |
| `events` | Stream: `tool_started`, `result_shown`, `email_given`, `full_view_opened`, `re_run` | none; capped at about 50000 entries |
| `gtm-unlocks` | List read by the daily digest; unchanged shape, ICP unlocks now land here with `tool: "icp"` | none |

- The old `gtm-submissions`, `icp-submissions`, `gtm-text:*`, `icp-text:*`, `gtm-details:*` and `icp-details:*` keys are no longer written. They are left in place; no migration.
- Changing a model: `/admin/models` shows one row per routing key (`scoring`, `details`, `synthesis`, `extraction`) with the current model and live price, reasoning, calibration state, and calls and spend over the last 30 days. Pick a model from the dropdown (curated list only) and save; the change is live within 30 seconds, no deploy. "Add per-tool override" creates a `{task}:{tool}` row that wins over the task row for that tool only. "Reset to default" deletes the override and the key's calibration record. Changing `scoring`, `scoring:{tool}` or `synthesis` marks that key "Uncalibrated since" until the calibration script records a pass with that model; `details` and `extraction` are not gated. Reasoning is off for `scoring` (Haiku 5.5 allows it) and low for `details`, `extraction` and `synthesis` (medium). Sonnet and Opus class models through OpenRouter refuse to disable reasoning with a 400 "Reasoning is mandatory"; if a key is set to a model that refuses, the client resends once with low effort and the call log shows `reasoningFallback: true`. The 5.x models think before answering and thinking tokens count against max tokens, so if you turn reasoning on for a key in `/admin/models`, raise that key's max tokens to cover the thinking plus the answer (a scoring answer is about 150 tokens; thinking adds hundreds to thousands) or calls fail with 502 and `ai:calls` shows "ran out of tokens". Keep `details` reasoning off or low: a heavy reasoning model on a 3000 token answer can approach the 60 second limit. Any saved change on `scoring`, `scoring:{tool}` or `synthesis`, including a reasoning change, marks that key uncalibrated.
- Changing a rubric or system prompt: edit the row in the Notion "Tool Rubrics" database (page body is the rubric, the System Prompt property is the prompt), bump Version, set Status to Published. The site picks it up within 10 minutes, or at once after the refresh button on `/admin/rubrics`, which clears every `rubric:*` key (each warm instance then catches up within its 60 second memory cache). Then run `npm run calibrate`. Every run stores the rubric hash it was scored with, so results are traceable across versions.
- Calibration: `npm run calibrate` (reads `.env.local`; needs the OpenRouter, Notion and Upstash variables when at least one case is runnable). It scores every `calibration/{tool}/*.json` case through `scoreRun`, compares the overall grade and each dimension grade with `expected`, prints a table and exits `0` when every run case is within one point (or nothing was runnable), `1` when a grade moved by more than one point or a case threw, `2` when configuration is missing. A case whose input contains `TO FILL` is reported as skipped and never scored; a folder with no public registry entry (`built-to-scale`, `route-to-buyer`, `unit-of-value`) is reported as skipped too. On a full pass with at least one case run it writes `admin:calibration` for every scoring key used, which `/admin/models` shows as "Passed with {model} on {date}". Calibration runs are not stored in `run:{id}`; they appear in `ai:calls` with a `cal_` run id. See `calibration/README.md` for the case format.

**To disable:**
- One tool, no deploy: set its row to Draft in Notion and press refresh on `/admin/rubrics`. That tool answers 503 "rubric not published" until the row is Published again; the other tools are unaffected.
- All scoring, no deploy: remove `OPENROUTER_API_KEY` from Vercel and redeploy the environment. Every score and details call answers 503 "model provider not configured"; pages still render.
- One tool permanently: set `hidden: true` on its registry entry and deploy. It leaves the hub, the sitemap params and the three routes (404).

## Unlock gate, emailed result and delete-my-data, added October 2026

**Trigger:** A visitor scores a tool at `/tools/{slug}` and presses "Unlock and email my result" on the gate (email required, name and company optional, honeypot unchanged). From then on, for 30 days, every tool on that browser skips the gate: the score response carries `unlocked: true` and `ToolPage.tsx` requests details straight away. The first full view for a run sends the result by email with a saved link and a delete-my-data link. Opening the saved link (`/tools/{slug}?run={runId}&t={token}`) shows that run's full view with the inputs hidden until "Score again". Opening the delete link (`/api/tools/data/delete?e={emailHash}&t={token}`) shows a confirmation page; pressing "Delete my data" removes every run stored under that email.

**Service/Function:**
- `app/lib/tools/unlock-token.ts` is the pure HMAC-SHA256 module (`signToken`, `verifyToken`, `hashEmail`). Secret and clock are arguments. One module, three purpose strings: `unlock-cookie`, `saved-link`, `delete`. A token issued for one purpose fails for another.
- `app/lib/unlock.ts` is the only reader of `UNLOCK_SECRET`. Exports the cookie name and options and the typed issue and verify helpers the routes use.
- `app/lib/mail.ts` is the one nodemailer transport (`sendMail`, `isMailConfigured`, `resultFromAddress`). The daily digest now sends through it with no timeout; the result email passes a budget.
- `app/lib/tools/result-email.ts` renders the subject, plain text and text-first HTML. `redactAddresses` strips anything shaped like an address from a transport error before it is logged.
- `app/api/tools/[tool]/unlock/route.ts`: validates (email only), `markUnlocked` (records the unlock, PERSISTs the run, SADDs the id to `runs:by-email:{hash}`), appends to `gtm-unlocks` with `name` and `company` as `""` when absent, tracks `email_given`, and sets the cookie when the secret is set. Responds `{ ok: true, unlocked }` where `unlocked` is true only when a cookie went out.
- `app/api/tools/[tool]/score/route.ts`: unchanged through `scoreRun`; afterwards reads the cookie and responds with `unlocked: true` when it verifies. Nothing is written to the run at score time.
- `app/api/tools/[tool]/details/route.ts`: body `{ runId, token? }`. Order: parse, slug, runId; verify cookie and token (string checks only); read the run; stored early return with `emailed: false`; 403 when neither the record, the cookie nor the token authorises; limiter; `detailRun` with the verified claims; email once; respond with the full view plus `emailed`. `detailRun` records a cookie unlock on the run (hash only, empty name and company) before generating, so the run persists and is indexed. `full_view_opened` carries `via: form | cookie | link`.
- `app/api/tools/data/delete/route.ts`: GET and POST both verify the token against the hash. GET renders the confirmation page; POST calls `deleteRunsByEmail`, tracks `data_deleted` with the count only, clears a `summit_unlock` cookie whose hash matches, and renders the Done page. Plain HTML strings, inline BRAND styles, no script.
- `app/lib/runs.ts`: `emailStatus` (`sent`, `failed`, null) and `emailedAt` on the record; `emailIndexKey`, `getRuns`, `listRunIdsByEmail`, `deleteRunsByEmail`, `recordEmailStatus`.
- `app/components/toolkit/ToolPage.tsx`: email-first gate, skips the gate on `unlocked`, `SavedResultLoader` (under Suspense so the tool pages stay static) reads `run` and `t` and loads the saved view.

**The cookie:** name `summit_unlock`; httpOnly; `secure` in production (follows `NODE_ENV`, so `npm run dev` over http still sets it); SameSite Lax; path `/`; Max-Age 30 days. Value is a signed token with purpose `unlock-cookie` carrying `eh` (the SHA-256 hash of the trimmed, lowercased email) and `iat`. Never the address. The 30 days is enforced twice: on `iat` at verification, and by Max-Age in the browser. Each form unlock issues its own cookie; two devices hold two valid cookies with the same hash and nothing revokes them except expiry, a secret rotation, or the delete flow clearing the one it can see.

**The links:** the saved link token (purpose `saved-link`, claim `run`) and the delete link token (purpose `delete`, claim `eh`) do not expire. Each is bound to one run id or one email hash and does nothing for any other run, hash or route, so there is nothing to gain from an old link beyond what its owner could already do. The URLs use the request origin, so a preview deployment emails links to itself rather than to production.

**Failure mode:**
- `UNLOCK_SECRET` unset: the unlock still records on the run (per-run, as before 1b); no cookie, no saved link, no email. The visitor sees the full view for that run but is gated again on the next tool. Every run shows `emailStatus: failed` with the log line "UNLOCK_SECRET is not set"; the warning "UNLOCK_SECRET is not set: unlocks are recorded but no cookie, saved link or result email is issued" logs once per instance.
- SMTP variables unset, or the send fails or times out: the visitor sees the full view without the "on its way to your inbox" line; the run records `emailStatus: failed`; the log carries the hash prefix and the transport error with addresses redacted. A `failed` status is final: there is no resend path in this release.
- Send budget: the transport gets 58 s minus the time since the handler started, capped at 10 s, and is skipped under 2 s (logged "no time budget for email"). The full view is already persisted by then, so the request stays inside `maxDuration = 60` and a retry serves the stored view.
- Cookie unlock with no address on record (the visitor deleted their data, then unlocked another tool with the surviving cookie): the run is unlocked and the full view shown; the send is recorded `failed` with "no address on record for hash".
- Run expired or deleted: a saved link gets 404 from the details route and `ToolPage` shows the normal empty page with no error. A visitor with a cookie whose run was never persisted (Redis down at score time) gets 404 on details and falls back to the gate.
- Invalid or tampered cookie: treated as no cookie; the gate shows. Invalid saved link (wrong token, wrong run, rotated secret): 403, normal page. Invalid delete link: a 400 "This link is not valid" page with no button. A delete POST without a valid token: the same page; nothing is deleted.
- Redis down: unlock and details answer 500 as in 1a; the delete POST renders a 500 "Something went wrong. Please try the link again in a few minutes." page and is safe to retry (the route is idempotent). Opening a delete link a second time renders "Done. There was nothing stored under this address."
- Secret rotation: every cookie, saved link and delete link issued under the old secret stops verifying at once. Visitors see the gate again on their next score and emailed links show the normal page or the "not valid" page. No overlap window exists in this release.

**Template/Config:**
- `UNLOCK_SECRET`: required in Production, Preview and Development on Vercel before this ships. Generate with `openssl rand -hex 32`. Signs the cookie and both links. Read in `app/lib/unlock.ts` only.
- `RESULT_FROM_EMAIL`: optional; the From address on the emailed result. Defaults to `SMTP_USER`.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`: unchanged; now read by `app/lib/mail.ts` for both the result email and the daily digest. `NOTIFY_EMAIL` is still the digest's From and To.
- Redis keys:

| Key | What | TTL |
|---|---|---|
| `runs:by-email:{emailHash}` | Set of run ids unlocked under that hash (form or cookie). Written by `markUnlocked` from this release on; runs unlocked before this deploy are not in it | none; deleted by the delete flow |
| `run:{id}` | Gains `emailStatus` (`sent`, `failed`, or absent when no send was attempted) and `emailedAt` (ISO, set on a send). A cookie unlock stores `unlock` with the hash and empty `email`, `name` and `company` | unchanged |
| `events` | Gains `result_emailed` (`tool`, `runId`, `emailHash`) and `data_deleted` (`count` only). `full_view_opened` gains `via` | unchanged |
| `gtm-unlocks` | Unchanged shape; 1b entries carry `name` and `company` as `""`. Cookie unlocks do not append (the lead was reported when the email was first given). Not purged by the delete flow | none |

- Copy: gate heading "Unlock the full view", one line on what the email is used for, button "Unlock and email my result", footnote on the saved and delete links. Email subject "Your {tool} result: {score} out of 100, grade {grade} of 5"; body in registry order with both links and the line "This result was produced automatically against Summit Strategy Advisory's rubrics." The template replaces any en or em dash the model wrote.
- Preview deployments: the cookie is set on the preview host and emailed links point at the preview origin, which shows Vercel's login to anyone without access. Run previews with SMTP unset or pointed at a test inbox.

**To disable:**
- Cookies, saved links and result emails, no deploy: remove `UNLOCK_SECRET` from Vercel and redeploy the environment. The gate falls back to per-run unlocks (name and company still optional), unlocks still record on the run and in `gtm-unlocks`, every run records `emailStatus: failed`, and the warning logs once per instance. Existing cookies and emailed links stop verifying.
- Result emails only, no deploy: set the SMTP variables empty and redeploy. Cookies and saved links keep working; the send fails before touching the network ("SMTP not configured") and is recorded `failed`. The daily digest stops too, since it shares the transport.
- The delete route cannot be switched off without a deploy; it only ever deletes data under a signed hash, so there is no reason to.

**Follow-ups (from the review, non-blocking):**
- Live smoke on a preview with `UNLOCK_SECRET` set and SMTP at a test inbox: the cookie flow, the emailed result, the saved link, the delete flow and the `runs:by-email` index have unit coverage for their pure parts only.
- Timeout stacking: nodemailer's connection, greeting and socket timeouts each get the remaining budget and run one after another, so a host that stalls at every stage could exceed it. Race the send against the remaining budget.
- Route the three legacy transports (`ai-studio-request`, `admin/reset-request`, `crm-interest`) through `app/lib/mail.ts`.
- `signToken` spreads claims after the header, so a claim named `v`, `p` or `iat` would override it. All callers use fixed names; add a guard before reusing it with caller-supplied names.
- Runs unlocked before this deploy are not in `runs:by-email`, so a delete link does not cover 1a-era runs. A backfill (iterate `runs:by-time`, SADD by `unlock.emailHash`) is a short script if wanted.
- Owner decisions: the delete POST clears a matching unlock cookie (not in the spec); `gtm-unlocks` is not purged on delete (needs an LREM scan or a digest rebuilt from the run store).
- No resend path for `emailStatus: failed`; `emailStatus` is not shown on `/admin/runs`.

**Failure mode:**
- `UNLOCK_SECRET` unset: the first save still records the brief and answers `token: null`, `emailed: false`; the page shows "Your brief is saved, but the link could not be emailed." No resume link, no autosave (the page has no token to send) and Submit shows the same line; admin Unlock sets the status and reports the email could not go; the cron sends no reminders. The log line is "UNLOCK_SECRET is not set" with the hash prefix.
- SMTP unset or failing: every send fails inside `sendBudgeted` ("SMTP not configured", or the transport error with addresses redacted), `lastEmailStatus: failed` on the record, and the save, submit or unlock still completes. No alert reaches Anthony, no reminder goes, and the change request is recorded on the brief only. `NOTIFY_EMAIL` unset: the alert and the change request email are skipped with a log line; the prospect's emails still go.
- Notion: `NOTION_BRIEFS_DB_ID` unset means `notion: "skipped"` and no page, nothing else changes. A write that fails after three attempts in all (a 429, a 5xx or a network error, 1 s then 2 s between, 8 s per attempt) or at once on another 4xx (a missing or mistyped property is a 400 no retry would fix) sets `notionStatus: failed`, adds a line to the alert, shows "failed" on `/admin/briefs`, and never blocks the prospect. Saving any status from admin retries the properties; the body is only appended on submit.
- OpenRouter down, `OPENROUTER_API_KEY` unset, an unusable answer, the per brief cap or the daily cap: `suggest`, `lookup` and `ideas` answer 200 with the rule based result and `fallback: true`, and the page shows one line ("The helper is not available just now, so this is the rule based suggestion.", "You have used the 30 suggestions for this brief. This is the rule based suggestion.", "The helpers have reached today's limit. Fill this step by hand.", "That's the limit on fresh ideas for this brief."). The event records `fallback: true`, so `/admin/stats` shows how often the model was absent. `read` has no rule reader: a failed call is 502, a missing key 503, the daily cap 429 with `Retry-After` to midnight UTC, and the page tells the prospect to fill the steps by hand. The daily reservation is spent even when the call fails; a provider outage with the Sonnet fallback in play can burn reservations. Reset by hand with `DEL builder:calls:{day}` (the day is UTC, `YYYY-MM-DD`).
- Redis down: the first save answers 500 "Could not save just now. Your brief is still on this device."; the helpers show "That did not work just now. You can carry on and fill this step by hand."; autosave shows "Could not save just now; your changes are kept on this device." and keeps the state; resume fails and the page shows "That link is not valid or has expired. Ask for a fresh one below." and keeps its local state; the delete POST renders the 500 page and is safe to retry; the admin pages show one error line each. Every step still renders. Without Upstash variables the limiters are off and the daily cap allows every call.
- A submitted brief: PUT, every helper and a second submit answer 409 with `locked: true` and "This brief has been submitted. Ask to change something from your brief page and Anthony will reopen it." The page switches to the read only view from the state it has. A change request on a draft answers 409 the other way ("still open: make the change in the builder").
- A resume link with a wrong token, a token for another brief, a token over 30 days old or a rotated secret: 403; the page shows the invalid link line and stays on whatever it had locally. An unknown or expired id: 404. A delete link that does not verify: the 400 "This link is not valid" page with no button. Opening a delete link a second time: "Done. There was nothing stored under this address."
- Honeypot filled (top level `website`): `{ ok: true }` and nothing stored or sent. A body over 60,000 characters of `source`: 400. A state that is not an object: 400. An unknown `step` or event name: 400.
- Time budget: the save, submit, change and link handlers read `startedAt` first; Notion runs before the mails so its worst case (about 30 s) cannot starve them; a send with under 2 s left is skipped and recorded `failed` with "no time budget for email".
- Two tabs or two devices on one link: last PUT wins. A reminder never refreshes the TTL. Calls made before the first save log `runId: null`, so cost per submitted brief on the stats page is total builder spend over submits, not a per id sum.

## Ask Summit to score it, added October 2026

**Trigger:** The third card on `/tools` ("Ask Summit to score it") now links to `/tools/ask-summit` instead of the mailto and has lost its "Coming next" tag. A prospect gives their website address (http or https; a bare domain is given https), a company email (free mail domains such as Gmail, Outlook, Hotmail, Yahoo, iCloud and Proton are refused with a plain message), optionally their name and company, up to three documents (PDF, PPTX or DOCX, 25 MB each), and ticks the consent line, which states the 30 day retention, that nothing they send is used to train any model, and that the confirmation email carries a delete-my-data link. The page carries the automated wording for the preparation step and the human review promise ("a person reads the output, checks it, edits the scores and writes the commentary; usually within two working days"). On submit the browser uploads each file straight to Vercel Blob under a token issued per file by `POST /api/ask-summit/upload`, then posts the request to `POST /api/ask-summit/submit`, which stores it, enqueues one QStash message and sends the confirmation. QStash calls `POST /api/ask-summit/process`, which crawls the site, reads the documents, drafts the five Built to Scale? parts, scores them through the 3a orchestration and creates a draft report through the Release 4 store, then emails Anthony "ready to review" with the queue and editor links. Anthony opens the report in the Release 4 editor, where a "Drafted inputs" section shows the drafted parts with confidence and evidence, the pages read and the documents, and a "Re-run with these inputs" button. He corrects, publishes and sends the report by hand as the Release 4 entry describes; the prospect never receives the raw run and the system sends them nothing but the confirmation. Other triggers: the "Ask Summit" link in the admin nav and the "Ask Summit queued" card on the dashboard open `/admin/ask-summit`; the daily cron at 01:30 UTC calls the retention route; the 1b delete-my-data link now also removes the prospect's requests; the daily report cron checks the monthly spend threshold.

**Service/Function:**
- Public page `app/tools/ask-summit/page.tsx` (dynamic, reads the pause switch; metadata, canonical, in the sitemap) wrapping the client form `app/components/toolkit/AskSummitPage.tsx`. The form validates the URL and the email as it is typed through the same pure module the routes use, mints the request id (`ask_` plus 16 hex) on the first submit so the uploads can precede the submission, uploads each file with `@vercel/blob/client`'s `upload` to `ask-summit/{requestId}/{safe name}` with `access: "private"` and the id in the client payload, and shows a thank-you view with the site, the file names and the email address only. Any answer but a 200 abandons the id, so a retry mints a new one; the abandoned blobs are orphans the sweep removes after 48 hours. The honeypot is named `nickname`, not `website`, because the real website field would otherwise be a target for browser autofill.
- Upload token route `app/api/ask-summit/upload/route.ts` (`maxDuration = 15`): 503 when paused or when `BLOB_READ_WRITE_TOKEN` is unset (the form can still be sent without files); otherwise `handleUpload` with `onBeforeGenerateToken` checking the request id shape, the pathname under `ask-summit/{requestId}/` with exactly one more segment and no `..`, the extension, and the per-request count (INCR on `ask:{id}:uploads`, one hour expiry; the fourth file is refused), then a token restricted to the three content types plus `application/octet-stream`, 25 MB, a random suffix and 15 minutes' validity. The Blob access level is set by the client upload call because the 2.8.2 token cannot pin it; the server never exposes a url, so only the uploader of their own file could choose public, and the Blob store can also be set to private-only in the Vercel console. The completion callback only logs and never fires on a local host.
- Submit route `app/api/ask-summit/submit/route.ts` (`maxDuration = 60`), in order: parse; honeypot (200 with nothing stored); pause (503 with the "not taking requests" message); request id, URL, email, consent and file list validation (400 with the one message the form shows); limiter `rl:ask-ip` at 5 per IP per day, then `rl:ask-email` at 2 per email hash per day (429 with `Retry-After: 86400`); `head()` on each blob, trusting the stored pathname, size and content type rather than the client's claims; the record at `ask:{id}` claimed with HSETNX (a replay answers 409), with `deleteAt` 30 days from `createdAt` and the index entries; one QStash publish to the processing route with `retries: 2` (an unconfigured or failing queue leaves `enqueueError` on the record, the queue shows "needs Process now" and Anthony is emailed from `after()`); the confirmation email with a 10 second timeout (its status is stored as `confirmationStatus`); `ask_submitted` tracked; the response carries the host, the file names and whether the confirmation was sent, never a blob url or pathname.
- Processing route `app/api/ask-summit/process/route.ts` (`maxDuration = 300`, which needs Vercel Pro; the stage clock budgets 290 s so the route always answers inside it), in order: read the raw body and verify the `Upstash-Signature` against it with the current and next signing keys (503 when the keys are unset, so an unsigned call is never processed; 401 on a bad signature; no admin or secret bypass, local runs use the script); parse the id; load the record; answer 200 with `skipped` for a request already `done` or `failed`, one `processing` under 15 minutes old, one whose data was deleted, or when paused, so QStash never retries a handled outcome; claim the lock (`SET NX EX 360` on `ask:{id}:lock`, longer than `maxDuration` so a killed function's lock expires on its own) and HINCRBY `attempts`; track `ask_processing`; run `processRequest`; release the lock in `finally`. QStash retries therefore only matter when the platform itself failed to run the route.
- The stages, `app/lib/ask-summit/process.ts`, under the clock in `stage-clock.ts` (caps crawl 100 s, documents 40 s, extraction 60 s, scoring 120 s, report 5 s, finish 3 s; a stage the budget cannot fund to its minimum is refused and named, which is how the route reports which stage ran out of time rather than hanging). Each stage writes what it produced onto the record as soon as it finishes, so a later failure leaves the earlier results visible. (a) Crawl, `crawler.ts` with the rules in `crawl-rules.ts`: robots.txt first (prefix rules for the `SummitBot` token or `*`, longest match wins, allow on a tie, `Crawl-delay` honoured up to 5 s and then one request at a time, otherwise four), the start URL then same-host links (one leading `www.` stripped; subdomains are other hosts), highest scored first (product, pricing, customers, about, team, solutions and case studies up; blog, legal, sign-in and listings down), 40 fetched pages, 1.5 MB of text, 10 s per page, no JavaScript, no forms, no cookies, no query strings beyond the start URL, visible text only, duplicates and shell pages skipped; stored at `ask:{id}:pages`. (b) Documents, `documents.ts`: each blob downloaded, its magic bytes checked against its extension (this is where the check happens, not at submit, because it is the first point the server holds the bytes), DOCX and PPTX unzipped with `fflate` and the text pulled from `word/document.xml` and `ppt/slides/slide{n}.xml` by `office-text.ts` (200,000 characters each; images are ignored), PDFs kept in memory for the model (20 MB each, 30 MB together, else skipped as too large); the list stored at `ask:{id}:docs`, PDF bytes never stored. (c) Extraction, `extraction.ts`: one `callModel` on the `extraction` routing key, temperature 0, the house-rules system prompt from `extraction-prompt.ts` (a code constant; see follow-ups), the pages and document texts as the user content inside a 160,000 character budget (documents keep up to 40 percent, the longest texts are trimmed first with a `[cut]` marker), the PDFs as file parts through OpenRouter's native engine, and the strict schema from `extraction-schema.ts` (five parts, each `text`, one or two `evidence` snippets, `confidence` low, medium or high with a `reason`, plus `companyName` and `summary`; an unsupported part comes back with empty text and low confidence). The call is raced against the stage allowance; when it fails with files attached and a full extraction minimum is still left it is retried once with no files and the PDFs marked as not sent (`pdfDropped`). The draft is stored at `ask:{id}:draft` with no expiry. (d) Scoring: `partsForScoring` replaces any part under 40 characters with a one-line placeholder saying the material did not cover it, so the 3a validator passes and the dimension scores as absent; then `scoreModel` with `source: "ask-summit"` and `requestId`, which stamps the composite run and tags every model call in `ai:calls`. (e) Report: `createReport` with the placeholder slug `draft-{last 8 of the run id}`, the company name from the extraction (the host when unknown), the extraction summary as the opening, the two other sections as "Anthony to write" and the new `askRequestId` field; a slug already taken means a retry got here first and the existing draft is kept; the run and its children are PERSISTed. (f) Finish: the record to `done` with `runId`, `reportSlug`, per-part confidence, page and document counts and timings; `ask_processed` tracked; Anthony emailed. Any stage failure sets `failed` with the stage and a redacted message, tracks `ask_failed` and emails Anthony; the function never throws past that boundary.
- Admin queue `app/admin/ask-summit/page.tsx`: the newest 100 requests with state (plus "stale" for a processing record older than 15 minutes and "needs Process now" when the publish failed), company, domain, email, files, pages, confidence summary, timings, data status (kept until or deleted on), the report and run links, attempts and created, with "Process now" (for `queued`, `failed` or stale, not one whose data was deleted: clears the failure and the stale lock, publishes again; `POST /api/admin/ask-summit/{id}` with `action=process`) and "Delete data" (removes the blobs, `ask:{id}:pages` and `ask:{id}:docs` and marks the record `dataDeleted`; keeps the request, the draft, the run and the report; `action=delete`). The pause switch at the top (`POST /api/admin/ask-summit`, `action=pause` or `resume`, tracked as `ask_paused` and `ask_resumed`) writes `admin:ask-summit:paused`; paused makes the form page show "Not taking requests right now", the token and submit routes answer 503 with the same message, and the processing route skip. Resume does not re-enqueue: press Process now on each queued request. Every control is a plain form POST answered with a 303 back to the queue carrying `?status=` or `?error=`.
- Editor section `app/admin/reports/[slug]/DraftedInputs.tsx`, rendered under the main editor form only when the report carries `askRequestId`: the request line (host, state, attempts, the extraction model, a PDF not sent, data deleted), the summary, the five drafted parts each with its confidence chip, reason and evidence quotes in a textarea (the edited text once a rerun carried one, marked "edited"), the pages read (folded past ten, with the robots status and skip counts) and the documents with their status and character counts. "Re-run with these inputs" posts to `POST /api/admin/ask-summit/rerun` (`maxDuration = 60`): the slug and request id must match, the lock is claimed without counting an attempt (so the queue's Attempts column stays the processing count), the posted parts go through the placeholder rule and the 3a validator, `scoreModel` runs as ask-summit with a 57 s deadline, the report is pointed at the new run with all five rows reset to it (`edited: false`; grade and comment edits are not kept, by design, and the status line says so; the three written sections are untouched), the previous run id is recorded on the request, the edits on the draft, and `ask_rerun` is tracked. The record's state is restored in `finally` on every path, so a failed rerun never leaves a done request reading as processing.
- Retention cron `app/api/admin/ask-summit/retention/route.ts` (`maxDuration = 60`; `vercel.json` schedule `30 1 * * *`, 01:30 UTC; `Authorization: Bearer {CRON_SECRET}` as the daily report): for every request past `deleteAt` and not yet cleared, delete its blobs, its pages and its docs and mark the record `dataDeleted` (tracked as `ask_data_deleted` with `reason: "retention"`); then sweep up to 1000 blobs under `ask-summit/` and delete orphans at least 48 hours old (an id with no record, or one already marked deleted). The pages and docs keys also carry EXPIREAT at `deleteAt` plus two days as a backstop, so a cron that is never configured still cannot keep crawled text past 32 days; blobs have no such backstop, the sweep is the only mechanism.
- Delete-my-data: `app/api/tools/data/delete/route.ts` now also reads `ask:by-email:{hash}`, deletes the blobs of every request under it, then removes each request's record, pages, docs, draft, lock and index entries, and says "n results and m requests deleted". The composite runs and the reports built from them are not touched (they are Summit's derived work and what a sent report is built on). Nothing uploaded is used for training; the consent line, the confirmation email and this entry say so.
- Spend: `app/lib/ask-summit/spend.ts` and `admin.ts`. `/admin/models` shows this UTC month's spend from `ai:calls` (the last 2000 calls; a call whose cost the provider did not report counts as zero, so it is a lower bound) and a threshold field saved to `admin:spend-threshold` through `POST /api/admin/ask-summit/spend-threshold` (a number of dollars, blank to clear). The daily report cron runs the check before its zero-lead early return, so a quiet day still alerts: when the spend has reached the threshold and `admin:spend-alerted:{yyyy-mm}` is unset it emails NOTIFY_EMAIL once ("model spend this month passed the threshold", with the queue and models links) and sets the flag; a failed send retries the next day. The pause switch is the manual response.
- Local processing `scripts/process-ask.ts`: `npm run process-ask -- {requestId}` runs the same six stages minus the signature check, for a machine QStash cannot reach or when QSTASH_TOKEN is unset. Needs the OpenRouter, Notion and Upstash variables in `.env.local`; `SITE_ORIGIN` sets the links in the alert (default `http://127.0.0.1:3000`). Exit 0 when the request reaches `done` (or was already done), 1 on a stage failure or a held lock, 2 for usage or missing configuration.
- Other modules: `validation.ts` (URL, same host, company email and the free-mail list, file types by extension and magic bytes, the limits, id and prefix shapes), `copy.ts` (every public string, tested for the house rules), `templates.ts` (the confirmation and the two alerts, pure), `notify.ts` (the sends; never throws), `queue.ts` (the only importer of `@upstash/qstash`), `blobs.ts` (the only server importer of `@vercel/blob`), `store.ts` (the Redis keys), `request-model.ts` (the record types and reader), `retention.ts` (the dates). `app/lib/llm.ts` gains `requestId` on the call log and `files` on `callModel` (PDFs as file parts, accepted on the `extraction` key only, sized before any call). The 3a result page `/tools/built-to-scale/r/{id}`, the details route and the OpenGraph image treat an ask-summit composite as admin only (404 or the empty frame without the admin session) so a leaked run id cannot show the raw run; Anthony opens the result page under his session to store the children's working for the report.

**Per request, in order:**
1. The "ready to review" email arrives, usually within five minutes of the submission. Open the queue link or the editor link.
2. In the editor, read the Drafted inputs section first: the confidence chips and reasons say where the material was thin, the evidence quotes say what the draft rests on, the page list says what was read and the document list whether a file was rejected, skipped or sent to the model. A row scored from a placeholder is a dimension the material did not cover, not a judgement on the company.
3. Correct the drafted parts where they are wrong or thin and click "Re-run with these inputs" when the corrections change the picture. The five rows reset to the new run; the opening, product thoughts and moonshot survive. Edit grades and comments only after the last rerun.
4. Finish the report as the Release 4 entry describes (company name and slug, as-of date, the three sections, grades and comments, Save, Publish) and send the link by hand. The prospect has only the confirmation until then.
5. When the request is no longer needed sooner than 30 days, click "Delete data" on the queue; otherwise the cron clears it.

**Failure mode:**
- Paused: the form shows "Not taking requests right now" with the contact address; the token and submit routes answer 503 with the same message; the processing route skips queued requests. Nothing is lost; resume and press Process now per request.
- Free mail address: refused at the form and again at the route with the message naming Gmail, Outlook, Hotmail, Yahoo, iCloud and Proton. A company whose own domain is on the list (Google, Microsoft, Apple, Proton, Yahoo staff) is refused too; the message names the contact address.
- `BLOB_READ_WRITE_TOKEN` unset: the token route answers 503 "Uploads are not configured" with one warning in the log; the form can be sent without files and the crawl alone feeds the draft.
- A fourth file, a wrong extension, a mismatched content type or a file over 25 MB: refused by the token, so the browser never uploads it; the form also checks each before upload. A file whose bytes are not what its extension says passes upload and submit and is marked "rejected: not a PDF" (or DOCX or PPTX) in the document stage; the draft is made from what remains and the editor shows the reason.
- `QSTASH_TOKEN` unset or the publish refused: the request is stored as `queued` with `enqueueError`, the queue shows "needs Process now", Anthony is emailed "needs Process now", and the confirmation still goes out. Fix the token and press Process now, or run `npm run process-ask -- {id}`. On a preview or any deployment behind Vercel's protection QStash cannot reach the route without `VERCEL_AUTOMATION_BYPASS_SECRET`; the same path applies.
- `QSTASH_CURRENT_SIGNING_KEY` or `QSTASH_NEXT_SIGNING_KEY` unset: the processing route answers 503 and logs the variable names; QStash retries twice and gives up; the request stays `queued` and the queue's Process now re-publishes once the keys are set. A bad signature answers 401 and is never processed.
- Running on the Hobby plan: `maxDuration = 300` is refused at build or capped at 60 s at deploy, and every request would fail at the first stage the clock refuses. Confirm Vercel Pro before the preview smoke.
- The site blocks bots, needs JavaScript or sits behind a challenge page: the crawl stores few or no pages (zero is a thin result, not an error), the draft comes back with low confidence and empty parts, the placeholder rule carries the run through, and the queue's confidence reads "0 high, 0 medium, 5 low". Nothing retries a blocked site; ask the prospect for a deck, or write the parts by hand in the editor and rerun. `ASK_SUMMIT_USER_AGENT` changes the user agent without a deploy if the default token is being blocked.
- A large site: `savePages` writes the whole crawl store (up to 1.5 MB of JSON) as one Redis string, and the Upstash free tier caps a request at 1 MB. The request fails at the crawl stage with the Upstash message. Lower `CRAWL_TEXT_CAP` in `crawl-rules.ts`, or move the store off the free tier.
- A PDF over the model's limits: over 20 MB (or 30 MB together) it is skipped as "too large for the model" in the document stage. Within the size limits but over the provider's page count, the first extraction call fails; the text-only fallback (pages and Office text only, PDFs marked not sent) only fires if the provider rejects the PDF within about 4 seconds, because the extraction minimum of 56 s must remain under the 60 s cap. A slower rejection fails the stage as "ran out of time" or with the provider's message; Process now tries again, or convert the deck to PPTX and resubmit. `pdfDropped` is shown in the editor either way.
- A DOCX or PPTX that is pictures only: read without error, with a small character count the editor shows; the draft is thin. Converting to PDF and resubmitting lets the model read the pages.
- The extraction returns five empty parts: allowed; every part becomes a placeholder, every dimension scores as absent, the report is created with the host as the company name and a thin opening. Visible in the queue's confidence column.
- A stage runs out of time: the record goes to `failed` with `failedStage` and "ran out of time before {stage}: n s left, m s needed", Anthony is emailed, and Process now runs the whole chain again (a new crawl, a new extraction call). The two model calls that cannot be cut short (extraction and synthesis) are abandoned one second before their deadlines; a late answer is logged when it settles.
- The function dies (a crash, a platform kill at 300 s): the record stays `processing`, the lock expires after 6 minutes, and after 15 minutes the queue marks it "stale" with a Process now button; the processing route also accepts a stale record. QStash's two retries cover a cold start or a killed function and are harmless under the lock and the state check.
- Scoring or synthesis failure: the usual 3a errors fail the scoring stage; the draft and the pages are already stored, so Process now only costs the model calls again. A `built-to-scale` rubric row not Published fails the scoring stage before any child call.
- A failed rerun from the editor: the state line shows "The change could not be saved" or "Every part needs at least 40 characters after the placeholder rule"; the request's state is restored and the lock released in `finally`, so it never shows as stale. "A re-run is already in progress" means the lock is held (a double click, or the processing route running); wait and try again.
- Redis down: the form renders (the page's pause read fails open; the submit route is the authority and answers 500 "Something went wrong"); the queue shows "The request store could not be read"; the processing route throws past the stage boundary and marks the record failed at `finish` when the write succeeds.
- SMTP or `NOTIFY_EMAIL` unset: the confirmation is skipped with `confirmationStatus: "unconfigured"` and the thank-you view says the confirmation could not be sent but the request is in; the alerts to Anthony are skipped with one warning per instance ("ask-summit alerts are off"). `UNLOCK_SECRET` unset: the confirmation carries the contact-address fallback instead of a delete link.
- Blob deletion fails during retention, the admin delete or the delete link: logged with the message cut to 200 characters, the Redis half still runs, and the sweep removes the blobs on a later night (a request already marked deleted counts as an orphan once its blobs are 48 hours old).
- Memory: three 25 MB files plus their base64 copies plus the crawl text approach 200 MB in the processing function; the default on Pro is 1,024 MB. PDF bytes are dropped the moment the extraction call returns.
- Derived data outlives the raw material: the draft, the composite run and the report stay after retention or the delete link. A delete-link request does not unpublish a report that names the company; that is Anthony's call in the editor.

**Failure mode:**

A Brandfetch logo address that refuses the fetch is skipped and the next candidate is tried, then the text wordmark.

**Troubleshooting:**
- "Up to date" in the dock but the server rebuilds, or the other way round: the dock hashes the contact as typed and the server hashes the stored contact, so the label can briefly disagree. The server's answer counts.
- The look is plain for a company with a site: check `brief-style:{id}` (or the House style row on the admin page) for `reason`, `source` and `brandLookup`. `unreadable` usually means bot protection, robots.txt disallows the crawler, the site needs JavaScript to render, or the host redirected somewhere refused. Then look at the brand lookup: `no-key` (set `BRANDFETCH_API_KEY`), `cap` (the day's cap is spent; it resets at midnight UTC), `miss` or `cached-miss` (Brandfetch does not know the domain; the miss is cached for 7 days, delete `brandfetch:{domain}` to ask again sooner), `error` (look for the `project-builder brandfetch:` log line).
- Forcing a fresh style read: the style is read once per brief and host and then reused. To read it again (for example a brief styled neutral before round 2, or after setting the Brandfetch key), delete the `brief-style:{id}` key in Upstash and press Update after any small change to the brief. An unchanged brief answers "up to date" without reading anything. Deleting `brandfetch:{domain}` as well forces a new live Brandfetch lookup, which spends one of the day's lookups.
- The new stats rows on `/admin/stats`: "Style from" counts style reads by source (Website, Brandfetch, Website and Brandfetch, Plain style). "Brandfetch" counts live lookups (hit, miss or error, the quota spend), brand found (hit or cached hit), from cache, not found, errors and daily cap reached. Brandfetch calls are not model calls and are not in `ai:calls` or the model cost rows.
- Every press fails with the first time wording: look in the function logs for `project-builder prototype: prototype failed: ...`. `time` means the plan's duration ceiling or a slow model; `invalid` means the model keeps returning broken structure (try the Sonnet fallback as the main model on `/admin/models`); `model` carries the provider error.
- "A prototype is already being drawn" after a crash: the lock clears itself within 300 s, or delete `brief-prototype-lock:{id}`.
- A prototype that shows a broken logo or loads nothing: the served document is re-sanitised on every read, so an older record is corrected when it is next served; if it still looks wrong, press Update after a change or delete `brief-prototype:{id}` to start again.

**Known limits and follow-ups (from the review, non-blocking):**
- SSRF: the style read and `fetchAsset` check the hostname only. A public name that resolves to a private IP is not caught, and with redirects followed only the final URL is checked. The Ask Summit crawler has the same limits. Follow-up: manual redirects with a check on each hop, plus a DNS resolve check.
- Frame self navigation: script inside the sandbox can still navigate the frame itself. The sandbox (scripts only, opaque origin) keeps the builder's own origin, cookies and storage safe; the CSP limits what the frame can load.
- `maxDuration = 300` needs a Vercel plan that allows it. With Sonnet at 24,000 tokens a full create can come close to the 210 s call cap (see Template/Config for the levers).
- Brandfetch logo addresses may refuse unsigned fetches; the next candidate is tried, then the wordmark. A site logo has no theme, so a light site logo on a light nav is still possible.
- The `brandfetch:{domain}` cache outlives a deleted brief by design (public brand data).
- The safety pass is regex based (no HTML parser is allowed without a new dependency); the CSP and the sandbox are the real boundary.
- No live run before this entry was written: the preview smoke test above is required before merging.

Suggest items are stored only. A recommendation naming a turned down idea is dropped and listed with "(turned down, not applied)". Stored at `brief-critique:{id}`. One review per full plan; none on a diff; a failed review never blocks |
| 4 Build | `builder-prototype-build` | Per screen: its plan entry, the items mapped to it, the profile, the house style lines, the shell's class names and the Round 2 build rules. Never the raw document excerpt | One call per screen in parallel, each returning `html`, `css` and `js` as separate fields. Each is checked in code (`checkScreen`): no `data-screen`, every id prefixed with the slug and unique, no id belonging to a longer planned slug, no banned tag, URL, `@import`, `url()` or outside-the-screen script, under the per screen budget. A failing screen is retried once with the issues named; if it still fails the previous build of that screen is kept when one exists, else the press fails with `invalid`. The server writes the shell (`renderShell`), places the screens, then runs the Round 1 safety pass and validator unchanged. Stored at `brief-prototype:{id}` with the Round 1 shape plus `planVersion`, `screens` (slug, model, ms, retried, kept), `screenBuilds` (the three parts per screen, so a later diff rebuilds only what changed), `stages` (stage, model, ms, ok) and `audit` |

Admin page only. Never blocks or changes the prototype. Skipped when the key is switched off in /admin/models or under 35 s remain |

The plan is saved after the prototype, so the stored plan always describes the stored document. Nothing is stored until a valid document exists. The side keys follow the brief's TTL through `briefSideKeys` (refreshed on a draft save, PERSISTed on submit, deleted with the brief and by the delete link). `brief-research-lock:{id}` (60 s) is held while a profile is built, by the save route in the background or by a press; a press that finds it held waits up to 10 s, then carries on with an empty profile.

**Change requests:** a request is a plan diff on `builder-prototype-plan`: the current plan, the request text (data in the user turn, under the data guard, never in a system prompt), the brief context and the profile go in; the whole updated plan, the slugs that changed and `outOfRemit` come back. A brief driven Update that is not a large change takes the same path with the lines from `describeChanges`. Only the changed screens are rebuilt; the first screen changing, more than half changing, or any screen added or removed rebuilds everything. The accepted request is carried in the plan's `accepted` list, so a later brief driven Update does not undo it. Every request is recorded at `brief-requests:{id}` (text, time, screens changed, model, outcome `built` or `declined`, newest last, at most 20) and listed on the admin page and the Notion page.

The box: label "What would you like changed?", a 600 character input and a Send button. It is enabled only when a prototype from the staged build exists (`planVersion > 0`), nothing is generating and requests remain. Enter sends. While it runs the same staged lines show and the previous prototype stays on screen. The answers:
- Built: the prototype refreshes in place, the note reads "Done. The prototype shows your change." and the text is cleared.
- Declined, outside the remit: the planner set `outOfRemit.refused` (sending messages, logging in to a real service, loading external content, real data, payments, anything not a change to the screens). The panel shows "That is outside what this prototype can show. It is a mockup of screens, so it cannot send messages, sign in to real systems or load live data." No build, no new version; the request is recorded as declined and still counts against the cap (a model call was spent). The text is cleared, since the server answered.
- Declined, nothing to change: the planner accepted it but no screen changed. The panel shows "Nothing on the screens needed to change for that. Your prototype is as it was." Same storage as above.
- Failed (502): "That change could not be made just now. Your prototype is as it was." The text is kept.
- 409 for a pre-Round 3 prototype (`planVersion` 0, a record from Rounds 1 and 2 with no plan): "Press Update prototype first, then ask for a change." The box shows the same line and is disabled until an Update has run the full pipeline.
- 400 under 4 characters: "Say a little more about the change, at least 4 characters."
- 429 at the per brief cap: "You have sent the most change requests this brief allows: 20 for each brief. Anthony will take it from here." A press at its own cap now says "...10 for each brief..." so the two caps read apart.
- 429 while a press or request runs: the Round 1 busy line, `Retry-After: 60`.

**Limits and caps:**
- Presses: 6 per IP per hour (`rl:builder-prototype`), 10 per brief that reach the model (`prototypeCount`).
- Change requests: their own per IP limiter of 20 per hour (`rl:builder-prototype-request`) and a per brief cap of 20 (`requestCount`), separate from the presses. A declined request counts.
- Daily cap: `BUILDER_DAILY_CAP` stays at 200. One reservation per press or change request, whatever the stage count (up to eleven model calls on a five screen first Create), and one per background research build at save. Per call counts go to `ai:calls` and the stats.
- Locks: `brief-prototype-lock:{id}` 300 s (shared by presses and requests), `brief-research-lock:{id}` 60 s.
- Time: the route budget is 285 s inside `maxDuration = 300`. Per call caps: 30 s research, plan, gap, diff and audit; 60 s review (raised from 30 s after the 9 November 2026 smoke test, where Opus 5.5 at medium timed out; the review needs 160 s left to start); 90 s per screen build and per retry. Each call's timeout is the smaller of its cap and the time left less the headroom. A stage that cannot start is skipped (gap, review, audit) or fails the press with `time` (plan, build). The save route's `maxDuration` is 90 so the background profile (40 s budget) fits after the save.
- Sizes: 3 to 5 screens; each screen's html, css and js together at most `min(16,000, (90,000 - shell - 1,000) / screens)` characters; the stored document still at most 90,000 characters after the safety pass; a request at most 600 characters.

**Failure mode:**
- Research cannot read the site and Brandfetch has nothing, or the call fails: an empty profile, the pipeline continues, the prompts carry "Company profile: none found." Research never fails a build. The empty profile is stored with the host so the next press does not try the same host again; delete `brief-research:{id}` to force a rebuild.
- Plan fails or under 100 s remain: the press fails with `model` or `time`, the previous prototype is kept, the route answers as in Round 1.
- Gap round or review fails: logged, the plan is used as it stands.
- A screen fails its check twice: the previous build of that screen is kept when one exists (`kept: true` on the record); otherwise `invalid` and the previous prototype is kept.
- The assembled document fails the Round 1 validator: `invalid`, nothing stored.
- Audit fails or is switched off: logged, the record keeps `audit: null`.
- A pinned provider is down: one resend on the fallback (see above). A timed out attempt is not resent.
- The other failures (daily cap, per brief caps, lock, per IP limit, `OPENROUTER_API_KEY` unset, Redis down) answer as in Rounds 1 and 2, with the new cap sentences above.

**Known limits (from the review, non-blocking):**
- Reasoning flag on the fallback leg: when a pinned primary falls back to an always model with the route at off, low effort is sent but `reasoningForced` stays false on that log row; `fallbackUsed: true` shows which model answered.
- Fallback timing: a pinned primary that fails fast is followed by one full attempt on the fallback under the same timeout, so a pinned model on the build key (an admin choice) can spend a fast fail plus 90 s. The defaults pin only research and audit, both non blocking.
- A request answered "nothing needed to change" is stored with outcome `declined`, so its Notion bullet carries the "outside the prototype's remit" suffix. Cosmetic; a third outcome would make it exact.
- Function death between the prototype save and the plan save: the record has `planVersion > 0` with no plan at `brief-plan:{id}`. The request route then answers "Press Update prototype first", while an unchanged brief answers "up to date". Make any small change and press Update; the run finds no current plan and replans in full.
- Unquoted ids: `checkScreen` and the validator read quoted `id="..."` only; an unquoted `id=foo` is invisible to both. Cosmetic, inside the sandbox.
- Parallel failure: `Promise.all` rejects on the first failed screen while the other in flight calls keep running and logging, so a failed press can still spend the remaining screen calls.
- The 30 s override cache: a switch flipped in /admin/models reaches a running function only on its next `resolveRoute`, within 30 s per process.
- Turned down ideas are kept out of the review by a substring match on the idea title; a reworded recommendation can pass, but it is only advice to the builder and never adds a requirement.

**Troubleshooting:**
- The prototype uses generic words rather than the company's: open Company profile on the admin page. `empty: true` with `sources.pages` 0 means the site could not be read (see the Round 2 notes on `reason` and `brandLookup`); delete `brief-research:{id}` and press Update after a small change to try again.
- A Must is missing from every screen: check Plan, Unplaced for the reason the planner gave, then Audit. A Must in the "Running it" category does not gate the plan by design.
- "Press Update prototype first" on a brief that has a prototype: the record predates Round 3 or the plan key is missing (see Known limits). An Update after any small change repairs it.
- A request keeps rebuilding every screen: the planner named the first screen, more than half the screens, or added or removed one. The Change requests section shows the slugs it changed.

## Project Builder prototype, design rules round, added November 2026

**Trigger:** The same Create, Update or change request press as Round 3. Nothing the prospect sees changes: the builder, the sandbox, the CSP, the safety pass, the validator, every route and the admin view are byte for byte as Round 3 left them. What changes is server side: the shell stylesheet written around every prototype, the design lines in the screen prompt, and two more per screen checks.

**Service/Function:** `shell.ts` (`resolveAccent`, `baseCss`, `SHELL_CLASSES`), `prompts.ts` (`DESIGN_CHOICE_RULES`, spread into `DESIGN_RULES` so both the screen and the fix prompt carry it), `screens.ts` (`checkScreen`, `DESIGN_ISSUE_LINES`, `isDesignIssue`) and the advisory block in `prototype-run.ts`. `house-style.ts` lends `contrastRatio` and is unchanged; the shell holds no luminance maths of its own.

**What the shell now enforces:**
- The evidence: on the 9 November 2026 live build of the Ocado brief the first brand colour is a light yellow, so filled buttons carried white text and figure values were yellow on white, on both models. The shell's fault, not the model's.
- The accent pair. `--accent` is the first brand colour that reads at 4.5:1 on the white surface; when none does, the first colour is darkened (each channel scaled by 0.9 and floored, so the hue holds) until it does; Ocado's `#F5D000` becomes `#816c00`. It carries figure values, secondary button text and border, links and every focus ring. Filled buttons and the active nav button keep `--brand-1` as the fill and take `--on-accent`: white when white reads at least as well on `--brand-1` as the text colour, else the text colour. Ocado yellow gets the dark text.
- One muted token, `--text-muted` (`#55636B`, 6.21:1 on white), on `pb-muted`, figure labels and deltas, field labels and detail terms.
- Hover and focus-visible states on buttons, nav buttons, inputs, table rows and list items, with one 150 ms transition on colour, background colour, border colour and box shadow only; the button hover is an inset shadow and the brightness filter is gone. `prefers-reduced-motion: reduce` removes transitions and animations.
- `cursor:pointer` on every button class, `pb-select` and `[data-go]`. A 24px minimum on every interactive class and `[data-go]`; 36px on buttons, nav buttons and inputs.
- Tabular figures on tables and figure values, plus three classes listed in `SHELL_CLASSES` so the prompt names them: `pb-num` (right aligned, tabular, no wrap, for numeric cells and headers), `pb-empty` (a dashed box with muted text in place of a list a filter has emptied) and `pb-field-error` (small `--bad` text under a field, hidden while empty).
- Size: the shell on the five screen neutral fixture is 9,425 characters (7,922 before, growth 1,503); `shellScreenBudget` still gives each of five screens 15,915. The `shell size` test pins both numbers.

**What the prompt asks for** (`DESIGN_CHOICE_RULES`: seven lines, 885 characters, sent once per screen per press): inline SVG icons with one stroke width and no emoji; every chart drawn complete in the html as SVG elements, with js only to filter; numbers, amounts and dates in `pb-num` cells and self coloured text in `--accent`; a hidden `pb-empty` box wherever a filter can empty a list; one `pb-field-error` sentence under a blank required field; status as `pb-label` text, never a coloured row or cell; one filled `pb-button` per screen, the rest secondary.

**The two new screen checks** (`checkScreen`, after the id checks and before the size line):
- Empty chart: an `<svg>` inside a `pb-chart` box with no `rect`, `path`, `polyline`, `circle` or `polygon` and at most two `line` elements. Issue line: `html: a chart in a pb-chart box has an svg with no marks drawn ...`. This is a small superset of the spec's element list on purpose: `polygon` counts as a mark, and two lines are the axes, so the 9 November chart that drew axes and a legend with no bars is caught. Do not expect a two line svg to pass.
- Coloured row: a screen css rule whose selector reaches `tr` or `td` and sets a `background` to anything but none, transparent, inherit, unset or initial, or an inline `style` with a background on a `tr` or `td`. Issue lines: `css: a rule on tr or td sets a background ...` and `html: a tr or td carries an inline background style ...`.
- Both go through the one retry like every other check. After the retry, or when the press has no time left for one, a screen whose only remaining lines are these design lines is accepted: the lines are stored as `notes` on that screen's entry in the record (only present when there are any; clean screens and old records have no such field) and logged with `console.info` as "accepted with design notes". Any blocking line keeps the Round 3 path: the previous build is kept on an Update, or the press fails `invalid` on a Create. `isDesignIssue` matches the three exact strings, so a blocking line is never read as advisory. `/admin/stats` does not count screens accepted with notes; its Fix retries column does rise when the checks trigger the retry.
- Known limits: a legend of small `rect` swatches beside line axes passes; a `pb-chart` box with no svg passes; a screen's own `tr:hover`, selected row or zebra cancel to a colour is flagged and retried.

**Old records and the theme's limits:** the shell is written per build, so a prototype stored before this change keeps its old CSS until the next press; the stored format gains only the optional `notes` field and `/admin/briefs/{id}/prototype` is unchanged. A dark site background is outside the shell's light theme. A mid tone brand (`#808080`) gets the better of white or the text colour on the fill and may sit under 4.5:1 on filled buttons, because the fill is fixed at `--brand-1`.

**Before and after comparison** (the measure of this round): the same Ocado brief (`brief_e7063bab84634459`, GPT-6 Astra on the build key), Create on the branch preview, each screen captured from `/admin/briefs/{id}/prototype` at 1,531 px wide, set beside the 9 November 2026 live build screenshots. A comparison page lists per screen: button text readable on the brand fill, figure values readable, hover and focus visible, numbers right aligned, chart drawn before any click, no coloured rows, an empty state after a filter that matches nothing, a field error on a blank required field, one filled button. Also note Fix retries on `/admin/stats` for the build key before and after, since the two checks can raise it.

**To disable:** no switch; the shell rules and the checks ship with the deploy, so revert the PR to remove them. A screen that trips a design check is never failed by it, so no running press needs intervention.
