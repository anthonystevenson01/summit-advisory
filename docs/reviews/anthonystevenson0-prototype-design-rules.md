**The Coder's note that the advisory path does not require `retried === true`.** Acceptable. The only way to reach the block without a retry is `remaining() < RETRY_MIN_MS`, that is, the press has no time left to retry. In that case the alternatives for a design only screen are kept previous (on an Update) or `invalid` (on a Create), which are the two outcomes the spec names as forbidden for a design line ("never kept-previous and never `invalid`", "never a hard failure"). Accepting the screen with the lines recorded is the reading that honours the spec on both paths; and when there is time, the checks still go through the one retry first, as the spec requires, because the retry block runs before the advisory block. Requiring `retried` would re-introduce a hard failure on exactly the path where the spec forbids one. The record's `retried: false` plus a `notes` field makes the no retry case visible when it happens.

## Loop 2: size tolerance

**VERDICT: APPROVE**

Scope: the uncommitted diff only. `app/lib/project-builder/screens.ts` (`SIZE_OVERRUN_TOLERANCE`, `SIZE_SOFT_MAX`, `sizeIssueLine`, `isSoftSizeIssue`), `app/lib/project-builder/prototype-run.ts` (the advisory condition), `__tests__/project-builder-screens.test.ts`, `docs/runbook.md`. Prompted by the 9 November 2026 preview, where `purchase-orders` came back at 16,037 characters against a share of 15,872 after its retry and the Create failed `invalid`.

### Checks

1. **`isSoftSizeIssue` matches only the size line.** [PASS] `SIZE_ISSUE_RE` is anchored at both ends and is literal text with two `(\d+)` groups separated by fixed words; no alternation, no nested or adjacent unbounded quantifiers, so matching is linear in the line and cannot backtrack badly. A design line (any of `DESIGN_ISSUE_LINES`), a check line, an `errorLine` or the empty string fails the match and returns false. The second group must equal the passed `budget` (`Number(m[2]) !== budget`), so a line written against another budget returns false. A size at or under the budget returns false, so the function cannot call a non overrun soft. `\d+` guarantees at least one digit, so `Number` never yields NaN; an absurdly long digit string gives a large number that fails `size <= limit`. `checkScreen` writes the size with plain `${size}`, no separators, so the regex reads exactly what it writes.

2. **The ceiling.** [PASS] `limit = min(floor(budget * 1.1), SIZE_SOFT_MAX)` with `SIZE_SOFT_MAX = floor(16,000 * 1.1) = 17,600` (the product is exactly 17,600 in double arithmetic; the test pins it). The Coder is right that a literal 16,000 ceiling would be wrong for the purpose: the preview case was 16,037, so a ceiling at the clamp would have refused the very case that prompted the change. `shellScreenBudget` already clamps every share to `SCREEN_BUDGET_MAX`, so the tolerance has to sit on top of the clamp or it is not a tolerance at all for a five screen build whose share is near the clamp. Ten per cent of the share is a judgement; it is bounded by the document gate below, so the worst it can do is move a failure from step 6 to step 7, never store a larger document.

3. **The hard gate holds.** [PASS] `assembleDocument` renders the shell, places the screens, runs `sanitisePrototypeHtml` and returns `validatePrototypeHtml(html)`, which pushes an issue when `html.length > PROTOTYPE_HTML_MAX_CHARS` (90,000, `prototype.ts:25`). In `prototype-run.ts` step 7, `if (assembled.issues.length > 0) throw new PrototypeFailedError("invalid", ...)` runs before step 8 `saveBriefPrototype`, so an oversized assembled document is never stored. Worst case for five screens: the share is `min(16,000, floor((90,000 - shell - 1,000) / 5))`. The preview share of 15,872 implies a shell of about 9,640 characters. Five screens each at that share's soft limit, `floor(15,872 * 1.1) = 17,459`, total 87,295, plus the shell gives about 96,935 before the wrappers, well over 90,000, so the press fails `invalid` at step 7. At the absolute ceiling, five screens at 17,600 are 88,000 on their own, which exceeds 90,000 with any shell over 2,000 characters; and for the clamp to be active at all the shell must be at most 9,000, so that case also fails `invalid`. In general the sum of the five shares is at most `89,000 - shell`, so the room the tolerance can actually use across a document is the 1,000 of `SHELL_HEADROOM` not taken by the wrappers plus whatever the other screens left under their shares. For the preview case (one screen 165 over, the others under) that is comfortably enough; five screens all over by one per cent (about 800 characters in total) would be close to the line and could fail at step 7 instead. That is the correct outcome: nothing oversized is stored, and the failure message then names the document rather than a screen. `parseScreenBuild` also still caps each field at `PROTOTYPE_REPLY_CHARS`, unchanged.

4. **The advisory block.** [PASS] The condition is `build && issues.length > 0 && issues.every((line) => isDesignIssue(line) || isSoftSizeIssue(line, budget))`. `every` is false as soon as one line is blocking, so a check line, an `errorLine` or a size line above the tolerance leaves `issues` populated and the code falls through unchanged to kept previous (Update, `kept: true`) or `throw new PrototypeFailedError("invalid", ...)` (Create). The `budget` passed is the same `shellScreenBudget` value `checkScreen` was called with on both the first check and the retry, so the budget equality in `isSoftSizeIssue` holds for lines the run itself produced. The design line path from loop 1 is unchanged apart from the log wording ("accepted with notes").

5. **The size line is unchanged.** [PASS] `HEAD` wrote `` `The screen is ${size} characters; it must be at most ${budget}. Shorten the sample data, not the components.` `` inline; `sizeIssueLine` returns the identical template. `screenFixPrompt` still lists `issues` verbatim (`- ${i}`), so the retry prompt is byte for byte the same.

6. **Tests and gates.** [PASS] The new `isSoftSizeIssue` block covers: the preview line (16,037 against 15,872, soft); `limit - 1`, `limit` (soft) and `limit + 1`, `2 * budget` (blocking) at the 15,872 share; `SIZE_SOFT_MAX` at the clamp (soft), `SIZE_SOFT_MAX + 1` at the clamp and at an over clamp share of 20,000 (blocking); the empty string, every design line, real blocking lines from `checkScreen`, a mismatched budget and a line at the budget (all false); and a round trip where the line `checkScreen` writes for a one character overrun is read as soft and a 50 per cent overrun is not. `limit` in the test is computed with the same formula as the implementation, but the fixed 16,037 case and the `17,600` assertion pin the behaviour independently. Re-run on this branch: `npm test` 630 pass, 0 fail; `npm run lint` 0 errors; `npx tsc --noEmit` clean.
