Add the Project Builder: six step brief, save and resume, submit

## What was built
A public page at `/tools/project-builder` where a prospect defines a software project in six steps with a one tap helper on every step, saves it and comes back by an emailed link on any device, and submits it to Summit, who sends the project brief within two working days (the prospect never sees a report or a download). The prototype's catalogue, requirements engine, prompts and rule based fallbacks are rebuilt as pure modules inside this Next.js site; briefs live in Upstash Redis, model calls go through three new routing keys, the emails through the existing mail transport, every submitted brief becomes a page in a Notion "Project Briefs" database, and a read only admin section lists briefs, shows one, sets its status, unlocks it and reports the funnel and spend.

## Architect decisions
- The engine (`app/lib/project-builder/`) is pure and shared by the page, the routes, the emails, the Notion builder and the cron, so the Must count on the dock, in the alert and in Notion is one number and "the same inputs produce the same rows" is tested offline. `catalogue.ts` has no imports at all.
- The brief state is the prototype's flat state object, validated and capped by `parseBriefState` on both sides; the pasted text is carried beside it and stored at its own key (`brief-source:{id}`) because it has its own 90 day TTL.
- Three routing keys by cost profile, none calibration gated: `builder-read` (Haiku, Sonnet fallback so an outage does not stop a read), `builder-suggest` (Haiku, small and frequent), `builder-ideas` (Sonnet, the one creative call). They appear on `/admin/models` like the others.
- The server applies every model result and returns the whole new state, so "fills blanks and adds, never overwrites" has one implementation (`apply.ts`, pinned by its own test) for the model path and the rules path alike. Undo is a client side snapshot.
- Any helper failure, including a missing provider key and the caps, answers the rule based result with `fallback: true` and one line on the page; the read route has no rule reader and answers an error instead.
- The brief id (`brief_` prefixed so it can never be mistaken for a run id) travels in `ai:calls` as `runId`, so cost per brief can be read from the log without touching `llm.ts` beyond the routing entries.
- Two new token purposes on the 1b module: `brief-link` (claim `b`, 30 days at verification, a fresh token per email) and `brief-delete` (claim `eh`, no expiry). Addresses never appear in tokens, URLs, logs or events.
- One Redis hash per brief with the run store's conventions: drafts expire after 183 days, a submit PERSISTs, an unlock restores the TTL; `briefs:by-updated` and `briefs:by-email:{hash}` mirror `runs.ts`.
- Notion is written as a value, never thrown, before the mails, with three attempts in all under an 8 s timeout each; the outcome lands on the record and in the alert. The body is appended on submit, not at save.
- Admin actions are plain form POSTs to one route with an `action` field; client fired events go through one whitelisted route that accepts two names and a step number and nothing else.
- The site wide cap is a UTC day counter reserved before each call and never refunded; `DEL builder:calls:{day}` is the reset.
- Prospect typed text never sits in a system turn: the business notes, the company name and a looked up system name all go in the user turn under the data guard, with the pasted material fenced.

Both are kept as written and can be reverted in a line each.
- **Non-blocking follow-ups from the review:** the purge pass does not prune index entries of hashes the TTL already removed (`listBriefs` prunes them on the next admin visit); Notion makes three attempts in all, not three retries; the link route has a timing side channel bounded by the 5 per hour limiter; on a 409 the page switches to the read only view from local state rather than reloading; `/tools` has a pre-existing 375 px overflow from hub elements outside this task; one assertion in `project-builder-requirements.test.ts` tests `String.replace` rather than `reasonSentence`; the daily cap is never refunded on a failed call.
